# uat-v2_021 incident

## 事象
- qwen3.5:122b の 1本目（Next.js Space Invaders）で Plan mode の iter 5 が 100 秒以上進まず、ESC 割り込みで停止した。
- 停止時点は `iter 5/50 duration 329s edited 0 files` で、実装作業に入る前だった。

## 問題箇所
- `src/agent/loop_run/turn.rs`
  - Plan mode の timeout 復旧順序が `main model timeout -> sidecar retry -> second timeout -> deterministic fallback plan` になっていた。
  - qwen3.5 系では non-streaming 90秒 timeout があるが、sidecar 再試行も待つため、Plan mode だけで 180 秒以上停止して見える。

## 根本原因
- local LLM 向けの Plan mode が、LLM の長考や停止を前提に十分単純化されていなかった。
- deterministic fallback plan は存在していたが、最初の timeout では使われず sidecar LLM へ再依存していたため、停止時間が長くなった。

## 対策案
- Plan mode の assistant reply timeout では、sidecar 再試行より先に deterministic fallback plan を materialize する。
- これにより、計画が止まった場合でもすぐ Act mode へ進められる plan を確定し、E2E の実装フェーズへ移れるようにする。

## 対策案詳細（仕様）
- `request_assistant_reply_with_retry` の transport timeout 処理で、`maybe_materialize_plan_after_timeout` を `maybe_fallback_plan_model_after_timeout` より前に呼ぶ。
- `should_materialize_plan_after_timeout` は、Plan mode かつ timeout error であれば `plan_model_override` の有無に関わらず true とする。
- deterministic fallback plan は既存の `deterministic_timeout_fallback_plan` を使い、要求ポート、対象 framework、検証手順、品質基準を含む。

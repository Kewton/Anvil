## 事象
- `qwen3.5:122b` で `uat_047` を実施したところ、Plan は承認まで進み、Act でも scaffold Bash は正常に成功した。
- scaffold 後の workspace には `app/page.tsx` と `next.config.ts` が存在していたが、その次ターンで focused `Read/Edit` には入らず、`thinking...` が再び 120 秒超継続した。
- つまり pre-read bounded 化を入れても、そのターン自体が focused mode 扱いになっていなかった。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- `has_successful_repo_edit(...)`
- `successful_repo_edit_count(...)`
- `post_scaffold_edit_recovery_target(...)`
- `post_scaffold_continuation_active(...)`

## 根本原因
- Act に入る前の Plan で、plan file に対する `Write/Edit` が複数回記録される。
- しかし `has_successful_repo_edit(...)` と `successful_repo_edit_count(...)` は plan file edit も一般の repo edit と同列に数えていた。
- その結果、Act 開始後に `post_scaffold_edit_recovery_target(...)` が「既に successful repo edit 済み」と誤判定して `None` を返し、focused tool制約、non-streaming override、timeout override の全てが無効化されていた。
- つまり問題は timeout 値ではなく、「Plan の編集履歴が Act の focused recovery を毒していた」ことだった。

## 対策
- plan file への `Write/Edit` を Act 側の repo-progress 判定から除外する。
- post-scaffold / continuation / first-slice note は「non-plan repo edit」のみを基準に判定する。

## 対策案詳細（仕様）
- assistant tool call と後続 tool result を対応付けて、`is_plan_file_tool_call(...)` に一致する `Write/Edit` は non-plan repo edit count から除外する。
- `post_scaffold_edit_recovery_target(...)`、`forced_small_edit_recovery_target(...)`、`empty_workspace_scaffold_policy_error(...)`、`post_scaffold_continuation_active(...)`、`build_request_messages(...)` の `successful_repo_edits` 判定を non-plan 基準へ切り替える。
- 回帰テストとして、plan file `Write` が先に存在しても post-scaffold continuation が有効になることを固定する。

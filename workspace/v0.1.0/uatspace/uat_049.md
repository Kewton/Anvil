## 事象
- `qwen3.5:122b` で `uat_049` を実施したところ、Plan は承認まで進み、Act でも scaffold Bash は正常に成功した。
- その後 `iter 2` で `Read src/app/page.tsx` までは安定して到達したが、次の first `Edit` turn で再び長考し、`iter 3` で `tool_call_format_error: truncated tool call (generate response hit length limit)` に落ちた。
- sandbox 上の `src/app/page.tsx` は default scaffold のままで、今回も実装 edit は 1 回も landing していなかった。
- つまり `uat_048` の対策で入れた exact old_string note でも、first `Edit` の長文化自体は止め切れなかった。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- `focused_edit_first_slice_note(...)`
- post-read focused turn の first `Edit` 制約
- focused `Edit` tool call 生成時の shape 固定不足

## 根本原因
- `Read` 済みの page component に対して exact `old_string` block を system note で与えても、モデルはなお first `Edit` turn で new UI を広く設計し直そうとし、tool call 本体を冗長に膨らませた。
- 現状の guidance は「どの block を置換するか」はかなり具体化できているが、「どの JSON shape で、どれだけ短く、どの程度の UI slice に限定するか」の拘束がまだ弱い。
- そのため `qwen3.5:122b` は first `Edit` を mini patch ではなく semi-complete page rewrite のように出しがちで、結果として length limit に達して truncated する。
- 要するにボトルネックは anchor の特定ではなく、post-read first `Edit` の出力スコープと tool-call body の肥大化抑制だった。

## 対策
- post-read first `Edit` では、anchor 指示だけでなく `Edit` の arguments shape 自体をさらに固定する。
- 特に page component の first slice は「HUD と playfield frame だけ」など実装スコープをさらに小さくし、1 turn で作る UI 量を減らす。

## 対策案詳細（仕様）
- focused page first-slice note を強化し、次ターンでは `Edit` 1 回のみ、`path` は target 固定、`old_string` は埋め込んだ exact block をそのまま使うことを明示する。
- `new_string` 側も「title / HUD / playfield frame / controls hint に限定し、説明文や装飾を広げすぎない」よう制約を追加する。
- 可能なら JSON wrapper 付きの mini skeleton を system note に与え、モデルが prose や余分な説明を足さずに tool call 本体だけを返しやすくする。
- あわせて focused page first `Edit` 専用の `max_predict` をさらに引き下げる、または page-first-slice 専用 prompt で context をさらに圧縮し、tool body が肥大化する前に切り返す。

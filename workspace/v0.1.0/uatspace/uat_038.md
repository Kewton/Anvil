## 事象
- メインモデルを `qwen3.5:122b` に切り替えて `uat_038` を実施した。
- empty workspace から scaffold は成功し、その後 `src/app/page.tsx` を単独で `Read`、続いて `Edit src/app/page.tsx` まで到達した。
- ただし `Edit` 実行後の継続 turn で再び長考に入り、品質安定の完了条件までは未到達。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- prompt / recovery 全体の post-edit 継続制御

## 根本原因
- `qwen3.5:122b` は `qwen3.6:27b-coding-nvfp4` より first `Edit` への収束が良く、`Read -> Edit` までは前進した。
- しかし edit 後に「続けて実装を進める」turn の収束はまだ弱く、tool call 後の継続 reply が長考に戻る。
- つまり主因はモデル選択だけではなく、post-edit / partial-progress turn を runtime 側でどう押し切るかに残っている。

## 対策
- `qwen3.5:122b` は first `Edit` 収束性が良いので、当面の main model として継続候補にできる。
- 一方で code 側では、edit 後の next-step prose / 長考停滞に対する partial-progress recovery をさらに強くする必要がある。
- 次は `repo_change_partial_progress_note(...)` の先で、次ターンを単一 focused `Edit` または検証 shell により明確に分岐させる方向で締める。

## 期待効果
- `qwen3.5:122b` の first `Edit` 到達率を活かしつつ、その先の実装継続率を上げられる。
- 「scaffold して読めるが edit 後に止まる」型の停滞を減らせる。

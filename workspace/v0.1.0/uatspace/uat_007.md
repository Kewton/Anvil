## 事象
- `sandbox_0424/uat_007` で UAT を実施したところ、Plan mode は Stage 2 まで進んだが、Stage 3 の次回 `qwen3.5:122b` 呼び出しで 2 分以上 spinner のみが続き、tool call もエラーも返らなかった。
- セッションログでは `ollama.generate.request` が `stream=true` で記録された後、`ollama.generate.response_raw` も `ollama.generate.error` も追加されなかった。
- 実際の TTY でも `thinking... (qwen3.5:122b)` が `120s` を超えて継続しており、`OllamaClient::new(..., timeout=120s)` の設定より長く張り付いていた。

## 問題箇所
- `src/agent/loop_run/turn.rs`
  - terminal 実行では `stream_output || stdin.is_terminal()` により、tagged-xml path でも streaming transport を強制している。
- `src/ollama/client.rs` / `src/ollama/parsing.rs`
  - generate streaming response は `BufReader::lines()` で body を待ち続ける設計で、今回の stack では idle stream を適切に打ち切れない。

## 根本原因
- `qwen3.5:122b` は native tool path から外した後、`/api/generate` の tagged-xml tool path で動いているが、このモデルでは streaming generate が安定せず、body が返らないまま長時間張り付くケースがある。
- runtime は terminal 実行時に streaming transport を優先するため、tool-calling に streaming が不要な tagged-xml path でも不安定な経路を選んでいた。
- 結果として、Plan mode Stage 3 の LLM 呼び出しが spinner のみで停滞し、UAT 上は「途中停止」に見えた。

## 対策案
- `qwen3.5:122b` の tagged-xml tool path では streaming transport を使わず、non-streaming generate に固定する。
- native tool path が安定しているモデルのみ streaming tool transport を許可する。
- 回帰防止として、streaming transport 選択の unit test を追加する。

## 対策案詳細（仕様）
1. `request_assistant_reply()` で transport 選択を helper 化し、`qwen3.5:122b + !native_tools_enabled` の組み合わせでは non-streaming を選ぶ。
2. それ以外のモデルは既存どおり、terminal なら streaming transport を使う。
3. helper の unit test を追加し、
   - `qwen3.5:122b` tagged-xml path は non-streaming
   - `qwen3.6:27b-coding-nvfp4` native path は streaming
   を確認する。
4. これにより UAT では `qwen3.5:122b` の plan / act が streaming hang を踏まず、既存の request timeout が効く non-streaming path で進むようにする。

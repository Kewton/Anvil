- 事象
  - `uat-v2_012` で Next.js scaffold 後、`src/app/page.tsx` に複数回の小さな Edit が重なり、要求されたスペースインベーダーではなく generic な placeholder UI になった。
  - さらに JSX が壊れた状態になり、`<a` の重複や scaffold の `next.svg` / `vercel.svg` / `Documentation` が残った。
  - その後、focused edit recovery が継続して長時間推論し、約 508 秒で割り込み終了した。

- 問題箇所
  - `src/agent/loop_run/turn.rs`
    - `post_scaffold_continuation_active`
    - `post_scaffold_continuation_recovery_target`
    - `focused_edit_recovery_target`
  - `src/agent/recovery.rs`
    - `post_scaffold_continuation_note`
    - `first_scaffold_shell_edit_exact_anchor_note`
    - `second_scaffold_shell_edit_exact_anchor_note`

- 根本原因
  - scaffold 後の回復処理が「初回の小さな Edit」だけでなく「2回目の小さな Edit」まで強制していた。
  - その結果、モデルが本来必要な実装全体に戻れず、既存 scaffold の小さな文言差し替えを繰り返した。
  - 小さな anchor に対して JSX 断片やリンクを混ぜる失敗が発生すると、壊れた構文をさらに小刻みに編集する状態になり、品質ゲート到達前に recovery loop が長引いた。

- 対策案
  - scaffold 後の focused edit recovery は「最初の repo edit が成功するまで」に限定する。
  - 初回 edit 後は continuation recovery を発火させず、通常の実装フローに戻す。
  - generic / placeholder / 要求ドメイン不一致は既存の repo change quality gate で検出し、完成判定だけを止める。

- 対策案詳細（仕様）
  - `post_scaffold_continuation_active` は常に false を返す。
  - これにより `post_scaffold_continuation_recovery_target` は target を返さず、`focused_edit_recovery_target` から 2回目以降の scaffold continuation が外れる。
  - 初回 focused edit recovery は維持し、scaffold 直後に何も実装しないまま停止するケースは引き続き防ぐ。
  - テストは「2回目の小さな Edit 強制が無効化される」ことを確認する期待値に変更する。

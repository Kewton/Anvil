- 事象
  - `uat_054` で `anvildev -m qwen3.5:122b -y --sidecar-model qwen3.5:9b --auto-plan` を実行したところ、Plan mode のまま Act に進まず停止した。
  - main planning model の後に sidecar model へ切り替わったが、`Acceptance Criteria` / `Quality Bar` / Stage 3 セクションを繰り返し編集し、`Execution Plan` / `Verification Plan` / `Risks / Fallbacks` が実質的にプレースホルダーのまま残った。
  - 380秒、11 iteration 時点で中断した。リポジトリ編集は 0 件で、Next.js アプリは生成されなかった。

- 問題箇所
  - `src/agent/loop_run/turn.rs`
  - `deterministic_timeout_fallback_plan` は timeout 用に存在するが、通常の plan incomplete retry では未完成計画を決定論的に materialize しない。
  - fallback plan の `Quality Bar` が具体的な repo artifact / file path を含まず、`lifecycle::quality_bar_has_repo_specific_anchor` の意図に対して弱い。

- 根本原因
  - Plan completion の失敗が timeout に限定して扱われており、モデルが tool call / prose を返し続けて同じ欠落セクションを往復するケースでは deterministic fallback が発動しない。
  - `PlanIncomplete` で停止する前に、既に把握できているユーザー要求・task profile・work root から安全な最小計画を確定する経路がない。

- 対策案
  - Plan progress retry が閾値に達した場合、`PlanIncomplete` で終了せず、既存の deterministic fallback plan を plan file に書き込み、Plan を approval-ready にする。
  - fallback plan の `Quality Bar` に `src/app/page.tsx` / `app/page.tsx` / `package.json` のような具体的な repo artifact を含め、既存の品質判定を満たすようにする。

- 対策案詳細（仕様）
  - Plan mode で `empty reply`、`no tool calls`、または `final prose but plan incomplete` が連続し `plan_progress_retries` 閾値へ到達した場合、active plan path に deterministic fallback plan を書き込む。
  - fallback materialization 後は `mode_state.plan_stage` を `Ready` に更新し、通常の approval flow に進める。
  - fallback plan はユーザー要求から port / platform / deliverable label を反映し、汎用性を保つ。
  - `Quality Bar` は実装対象ファイルや起動スクリプトなどの repo-relative artifact を明示し、抽象的な品質文だけで完了判定されないようにする。

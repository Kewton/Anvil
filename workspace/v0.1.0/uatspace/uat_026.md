## 事象
- `uat_026` では `create-next-app` の command 破損は解消し、`space-invaders` scaffold 後に `[Workspace Root Updated]` が入り、`app/page.tsx` の read までは進んだ。
- しかし最初の実装 edit には入れず、`ls` ループの後に `Read src/app/page.tsx` 失敗、`Read app`、`Read app/page.tsx` を繰り返したあと長時間 thinking し、repo edit なしで retry に戻った。
- `llm-io.jsonl` 上は focused recovery 相当の流れに見えるが、実際には `Read` を止め切れず、compaction 後は `Repo Context` も再注入されていた。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- `src/agent/loop_run/lifecycle.rs`

## 根本原因
- post-scaffold focused recovery の有効条件が `recent_scaffold_command_seen(&session.messages)` 依存で、late-turn compaction や compact-summary 後に scaffold command 本体が履歴から薄れると recovery 判定が外れる。
- recovery 中の「Read は 1 回まで / 既読なら Edit のみ」という制約は tool schema の絞り込みに留まっており、モデルが未宣言の `Read` を出しても実行段で拒否していない。
- その結果、モデルが `src/app/page.tsx` のような誤パス read や `app` directory read を繰り返しても、runtime が強制的に `Edit app/page.tsx` へ収束させられていない。

## 対策案
- post-scaffold recovery を生メッセージ推定ではなく、durable な runtime state で保持する。
- focused recovery 中の tool policy を実行時にも強制し、既読後の `Read` / `Bash` / `Glob` / `Grep` を明示エラーで拒否する。
- wrong-path read が出ても target を維持し、`app/page.tsx` への 1 compact `Edit` へ戻す。

## 対策案詳細（仕様）
- recovery state
  - `active_root` 更新済みかつ成功 repo edit なし、または dedicated recovery note が残っている間は post-scaffold recovery を維持する。
  - compaction 後でも消えない state / note を使い、`recent_scaffold_command_seen` だけに依存しない。
- tool gate
  - focused target が既読なら `Edit` 以外の tool call を実行前に拒否し、`Error: focused edit recovery only allows Edit on <path>` を返す。
  - focused target 未読でも、許可するのは target file への `Read` 1 回か `Edit` のみとする。directory read や別 path read は拒否する。
- 期待結果
  - scaffold 後の first-edit recovery が compaction 後も維持される
  - `src/app/page.tsx` 誤読や `app` directory read がその場で止まり、`app/page.tsx` の compact edit へ収束する
  - `uat_027` 以降で初回 repo edit 到達率が上がる

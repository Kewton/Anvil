- `qwen3.5:122b` で `uat_048` を実施したところ、Plan は承認まで進み、Act でも scaffold Bash は正常に成功した。
- その後の recovery は前進しており、`iter 3` で focused retry が入り、`iter 4` では `Read src/app/page.tsx` まで到達した。
- ただし `iter 5` の post-read focused turn で `Edit` に収束せず、約 227 秒後に `tool_call_format_error: truncated tool call (generate response hit length limit)` で停止した。
- sandbox 上の `src/app/page.tsx` は default scaffold のままで、実装 edit は 1 回も landing していなかった。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- `focused_edit_first_slice_note(...)`
- post-read focused turn の prompt 制約
- `FOCUSED_EDIT_POST_READ_MAX_PREDICT`

## 根本原因
- `Read src/app/page.tsx` の後も、モデルは `old_string` を自分で再構成して最初の `Edit` を組み立てる必要があった。
- しかし `Read` 結果は行番号付きであり、既存 note は「central copy block を anchor にせよ」とは指示していても、次の `Edit` で使う exact `old_string` 自体は与えていなかった。
- そのため `qwen3.5:122b` は first edit turn で still exploratory に長く出力しやすく、最終的に長すぎる `Edit` tool call が length limit に達して truncated した。
- さらに post-read の `max_predict=640` は、この verbose な first edit を許しすぎていた。

## 対策
- page component の first focused edit では、last `Read` から抽出した exact `old_string` block を system note に埋め込み、`Edit` を block-replace に収束させる。
- post-read focused turn の `max_predict` をさらに引き下げ、長すぎる first edit 出力を抑制する。

## 対策案詳細（仕様）
- latest target `Read` tool result から行番号を除去して plain source を復元し、`<div className="flex flex-col items-center gap-6 text-center sm:items-start sm:text-left">` から対応する `</div>` までの marketing copy block を抽出する。
- `src/app/page.tsx` / `app/page.tsx` の first-slice note では、従来の prose anchor だけでなく、その抽出 block を `old_string` として byte-for-byte で使うよう明示する。
- これにより first `Edit` を「既読ブロック 1 個の差し替え」に固定し、全文再構成や追加探索を避ける。
- あわせて post-read focused turn の `max_predict` を `640 -> 448` に下げ、tool call が冗長化する前に compact `Edit` へ収束させる。

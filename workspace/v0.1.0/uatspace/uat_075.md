# UAT 075: qwen3.6 empty Next.js workspace repeated exploration

## Context

- Model: `qwen3.6:27b-coding-nvfp4`
- Session: `/Users/maenokota/.local/state/anvil/sessions/019dbf74-6654-7130-ba35-93c9396e1fcf`
- Sandbox: `/Users/maenokota/share/work/localwork/codextest/sandbox_0424/uat_075`
- Prompt: `あなたが考える最高に面白くかっこいいスペースインベーダーゲームを3011ポートで起動可能なnext.jsアプリとして開発してください。`

## Symptom

After plan approval, the model ran `ls -la` in an empty workspace, then attempted another directory inspection instead of scaffolding or writing files. The run ended with:

```text
✘ missing_repo_edits  iter 5/50  duration 14s  edited 0 files
assistant kept stopping before making the requested repository edits
```

## Root Cause

The empty-workspace scaffold guard depended on `active_task_requires_nextjs_scaffold()`, but that method only inspected the Act-mode working-memory active task. After approval, the active task is an execution summary and may say only "local app" instead of preserving the original `next.js` wording.

As a result, the guard failed to recognize that the original user request required a Next.js scaffold, so the first `ls` was allowed and recovery notes pushed the model toward reading/editing nonexistent target files instead of forcing `create-next-app`.

## Fix

- Detect Next.js scaffold requirements from the active task, original user messages, and current plan contents.
- Add a deterministic empty-workspace fallback: when a Next.js task stalls on exploration with no repository edits, emit one `create-next-app` Bash command automatically.
- Keep the existing scaffold policy so non-scaffold Bash commands are blocked once the request is recognized.

## Verification

- `cargo fmt --check`
- `cargo test detects_nextjs_request_from_original_user_message`

- 事象
  - `uat_060` で `qwen3.5:122b` による auto-plan 実行中、Plan フェーズ iter 5 で `tool_call_format_error` により停止した。
  - エラーは `tool call parser failed: malformed tool call markup`。Plan ファイルへの部分的な書き込み後、長時間の推論を経て編集 0 件のまま REPL に戻った。

- 問題箇所
  - Plan mode の LLM 応答解析で malformed tool call markup が発生した場合、既存の plan progress fallback / deterministic fallback へ接続されず、terminal error として扱われる。
  - qwen3.5 の非 native tool call が不安定な場面で、計画ファイルを安全に補完できる文脈があっても E2E が中断する。

- 根本原因
  - qwen3.5 は Plan フェーズで長い思考後に XML/tool-call markup を崩すことがある。
  - 現行実装は empty reply や plan progress stall には復旧を用意しているが、parser failure は同じ Plan 進捗失敗として扱っていないため、fallback plan を materialize する前に終了していた。

- 対策案
  - Plan mode 中の `tool_call_format_error` は、任意の Act 編集エラーとは分離し、計画作成の失敗として deterministic fallback plan を materialize して復旧する。
  - 元タスク、検出可能な port / framework、task profile を使って汎用的な plan を書き、承認待ちへ進める。

- 対策案詳細（仕様）
  - 対象は `ExecutionMode::Plan` かつ `lifecycle::is_tool_call_format_error` が true の場合に限定する。
  - `materialize_deterministic_fallback_plan` を呼び、成功時は `Plan complete. Reply yes to execute, no to revise, or provide feedback.` を返して Plan 承認へ遷移する。
  - fallback は既存の `deterministic_timeout_fallback_plan` を再利用し、Next.js / port / UI task など検出済みの情報を保持する。
  - Act mode の malformed tool call は従来どおり失敗扱いにし、編集途中の曖昧な復旧は行わない。
  - 回帰テストを追加し、`cargo fmt --check`、対象テスト、`cargo test`、`cargo build --release` で検証する。

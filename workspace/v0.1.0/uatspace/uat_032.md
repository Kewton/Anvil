## 事象
- `uat_032` では empty workspace 初動が改善し、1 回 prose-only retry の後に `npx create-next-app@latest ...` が実行され、Next.js scaffold までは安定して進んだ。
- scaffold 後は `src/app/page.tsx` と `package.json` を read し、post-scaffold recovery により target も `src/app/page.tsx` に固定された。
- しかし first edit には入れず、`src/app/page.tsx` 未変更のまま長文 prose-only reply を返し、runtime 側で `MissingRepoEdits` 系 retry が発火した。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- `src/agent/recovery.rs`

## 根本原因
- post-scaffold focused edit 状態では runtime が `Edit` のみを公開していても、model は tool call を出さず prose-only completion を返すことがある。
- その場の retry note は generic な `repo_change_no_tool_recovery_note` だったため、「この状態では `src/app/page.tsx` に対する `Edit` 1 回以外認めない」という focused-edit 固有の制約を十分に再提示できていなかった。
- その結果、`Edit` だけが有効な turn でも model が長い説明文で token を使い切る経路が残っていた。

## 対策
- focused edit recovery target がある状態で tool call なし終了になった場合は、generic repo-change note ではなく専用 note を返す。
- 専用 note では `src/app/page.tsx` への `Edit` 1 回だけを要求し、`old_string` を直前 Read から厳密コピーすること、`Read` 再実行や prose-only reply を禁止することを明示する。

## 期待効果
- `uat_032` 型の「scaffold 成功 -> target read 成功 -> prose-only length stop」を、focused edit の実 tool call へ押し戻しやすくなる。
- empty workspace 初動 fix と組み合わせることで、次の主戦場を scaffold 前から scaffold 後 first edit へ移せる。

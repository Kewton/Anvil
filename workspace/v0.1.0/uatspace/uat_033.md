## 事象
- `uat_033` では empty workspace 初動が安定し、初手から scaffold Bash に入り、その後 `app/page.tsx` の read まで進んだ。
- しかし `Edit` だけが公開された post-scaffold turn でも model は `Now I'll create a fully-featured Space Invaders game...` という future-intent prose-only reply で token を使い切り、`app/page.tsx` は未編集のままだった。
- 追加した focused-edit no-tool note はこの turn では効かず、runtime は依然として generic な `repo_change_recovery_note` 系の branch を通っていた。

## 問題箇所
- `src/agent/loop_run/turn.rs`

## 根本原因
- 今回の stalled turn は `tool_calls_made_this_turn == 0` ではなく、`Read` 1 回は成功しているため `repo_edit_calls_made_this_turn == 0` の branch に入っていた。
- その branch は generic な `repo_change_recovery_note` を返すだけで、focused edit recovery target が存在し、しかも target が既読済みである事実を recovery note に反映していなかった。
- そのため `Edit` しか許されない局面でも retry note が弱く、model を `Edit` 1 回へ十分押し込めていなかった。

## 対策
- `repo_edit_calls_made_this_turn == 0` branch でも focused edit recovery target を確認し、存在する場合は generic repo-change note の代わりに `focused_edit_no_tool_recovery_note(...)` を返す。
- これにより「Read は済んだ。次は prose ではなく `app/page.tsx` への `Edit` 1 回だけ」という制約を、長考後 retry の経路でも維持する。

## 期待効果
- `uat_033` 型の `Read -> prose-only length stop -> weak retry` を、`Read -> focused-edit retry -> Edit` に寄せやすくなる。
- scaffold 後 first edit の停滞を、tool-less turn だけでなく read-only turn でも同じ方向に補正できる。

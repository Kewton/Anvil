## Scope

Additional diverse tests for current Anvil behavior after WorkMode / ModePolicy changes.

Models:

- `qwen3.6:27b-coding-nvfp4`
- `qwen3.5:9b`

The goal was not only to confirm deterministic fallback success, but also to expose normal LLM edit performance and unsupported-framework behavior.

## Summary

Total additional cases: 11

- Passed: 7

By class:

- Deterministic, mode-gated paths: strong.
- Answer-only/read-only: stable for no edits; qwen3.6 sometimes needs one recovery retry.
- qwen3.6 normal existing-file edits: usable on small focused edits.
- qwen3.5 normal editing/tool use: weak; tool-call markup failures remain common.
- Unsupported web frameworks: unsafe quality fallback interaction found.

## Detailed Observations

### Strengths

- Mode isolation is working for Python CSV, Docs, AnswerOnly, and TypeScript UI happy paths.
- TypeScript UI deterministic output remains high quality enough for `next build` and smoke tests.
- qwen3.6 can complete simple existing-code edits when the target is narrow and the file is small.
- Answer-only no longer forces repository edits.

### Weaknesses

- qwen3.5 remains unreliable for normal tool-driven edits. It can emit malformed tool calls or produce semantically wrong code even when tests are requested.
- Generic Python support improved compared with the earlier CSV-only gap, but without deterministic fallback it still missed requested test coverage.
- Unsupported web framework behavior is unsafe. The SvelteKit case proved that a quality fallback can target a non-entry config file and write React/TSX content into `vite.config.js`.
- Edit summary telemetry can underreport edits in at least one docs-edit run: README changed, but final summary said `edited 0 files`.

## Performance Assessment

### Deterministic fallback paths

Current performance: high.

- Fast: usually iter 1, 0 seconds.
- Stable: low model dependence.
- Risk: must remain strictly mode-gated and target-aware.

### qwen3.6 normal editing

Current performance: moderate.

- Good for small focused changes with direct file targets.
- Can recover from one prose-only turn and continue editing.
- Still misses secondary requirements, such as adding tests, unless prompt/tool flow strongly enforces them.

### qwen3.5 normal editing

Current performance: low.

- Tool-call format errors remain a major blocker.
- Semantic correctness is not dependable for code generation outside deterministic fallbacks.
- Best current use is deterministic paths or very constrained read-only answers.

### Unsupported frameworks

Current performance: unsafe.

- The system correctly avoided empty-workspace Next/React/Nuxt deterministic app fallback for SvelteKit at first.
- However, later quality fallback still misapplied UI replacement to `vite.config.js`.
- This should be treated as a high-priority quality bug before claiming broad framework support.

## Recommended Next Fixes

1. Restrict `first_existing_impl_target` / quality fallback to real UI entry files only. Do not allow `vite.config.*`, `next.config.*`, `nuxt.config.*`, package files, or unknown framework config files as replacement targets.
2. Add an unsupported-framework guard: SvelteKit/Astro/Solid should use normal flow only and never use React/Next/Nuxt deterministic quality replacement.
3. For normal Python tasks, add a verification policy that requires a test file or a self-test command when the user explicitly asks for tests.
4. Add qwen3.5-specific hardening for malformed tool-call markup after a Read, or route qwen3.5 normal edits through a smaller focused edit protocol.
5. Fix edited-file telemetry so successful `Edit` operations are counted even when final repo snapshot detection misses them.

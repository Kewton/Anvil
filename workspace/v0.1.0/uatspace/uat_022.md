## 事象
- `uat_021` では Stage2 の plan 更新自体は成功したが、その直後に plan が進まず長時間停止した。
- ログを見ると本体の plan 更新ではなく、`stage3 fallback` の sidecar 判定リクエスト (`contains_stage_three_sections`) の後で応答が返らず止まっていた。

## 問題箇所
- `src/agent/loop_run/lifecycle.rs`
- `src/ollama/client.rs`

## 根本原因
- Stage1 と Stage2 が埋まり、missing section が Stage3 だけになると、runtime は sidecar に「Execution / Verification / Risks が実質埋まっているか」を問い合わせる。
- しかし現状は、Stage3 がテンプレート placeholder のままでもこの判定を毎回呼び、しかも main client timeout 相当の長い待ち時間で block する。
- そのため、sidecar が詰まると user には「途中で止まった」ように見える。

## 対策案
- Stage3 fallback 判定は、少なくとも Stage3 に substantive な内容が一部でもある時だけ呼ぶ。
- さらに sidecar 判定は専用の短い timeout / 小さい max_predict で実行し、詰まってもすぐ false に戻す。

## 対策案詳細（仕様）
- `plan_needs_stage_three_fallback` に gate を追加する
  - `Execution Plan / Verification Plan / Risks / Fallbacks` のいずれかが substantive でない限り、sidecar fallback を呼ばない
  - テンプレート placeholder (`1. First slice:`, `-`) だけの状態では sidecar 判定をスキップする
- `OllamaClient` に Stage3 fallback 専用の短時間 classification helper を追加する
  - timeout は summary/classifier より短めにする
  - max_predict も小さく抑える
- sidecar 判定が timeout / transport error の場合は即 `false` を返し、plan 本体の Stage3 更新を続ける
- 期待結果:
  - Stage2 完了直後に sidecar 判定だけで長時間固まらない
  - Stage3 placeholder の plan はそのまま Stage3 更新へ進む
  - sidecar fallback は本当に曖昧な plan にだけ限定される

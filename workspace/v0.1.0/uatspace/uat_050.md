## 事象
- `qwen3.5:122b` で `uat_050` を実施したところ、Plan 承認後の scaffold Bash は正常に成功し、`iter 2` で `Read src/app/page.tsx` にも到達した。
- しかし次の post-read first `Edit` turn で再び長考し続け、`iter 3` で `tool_call_format_error: truncated tool call (generate response hit length limit)` に落ちた。
- sandbox 上の `src/app/page.tsx` は default scaffold のままで、今回も実装 edit は 1 回も landing していなかった。
- つまり `uat_049` で入れた exact old_string note の強化と `max_predict=320` でも、first `Edit` の肥大化は止め切れなかった。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- `focused_edit_first_slice_note(...)`
- `focused_edit_history(...)`
- page scaffold 後 first `Edit` turn での context の与え方

## 根本原因
- 現状は exact `old_string` block を note で与えていても、同じ request 内に直前の `Read src/app/page.tsx` の全文コンテキストも残している。
- そのためモデルは「どの block を置換するか」は理解できていても、ページ全体を再設計できる余地がまだ見えており、first `Edit` を局所 patch ではなく広い rewrite として組み立て続けた。
- ボトルネックは `old_string` 特定そのものではなく、「post-read first `Edit` の時点で full page context をまだ渡しすぎていること」と、「first turn の UI slice がまだ大きいこと」の組み合わせだった。

## 対策
- page scaffold 後の first `Edit` では、exact anchor が取れている場合に限って full `Read` 履歴を次ターンへ持ち込まない。
- その代わり、system note に exact `old_string` と小さい replacement shape だけを渡し、`Edit` のスコープを headline/copy の極小差し替えまで落とす。

## 対策案詳細（仕様）
- `focused_edit_first_slice_note(...)` が exact anchor を生成できるケースでは、follow-up turn に `Read` tool result 全文を再注入しない。
- page first slice の置換対象も marketing block 全体ではなく、`<h1>` から `</p>` までの intro copy block に縮める。
- note では `Edit` 1 回のみ、`old_string` は埋め込んだ exact block のみ、`new_string` は title + HUD line + controls hint 程度の極小 replacement に限定する。
- これでモデルに「全文を見直して大きく書き換える」余地を与えず、first `Edit` を確実に landing させる方向で再検証する。

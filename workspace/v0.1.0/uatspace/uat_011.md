## 事象
- `sandbox_0424/uat_011` で UAT を再実施したところ、main plan request `qwen3.5:122b` は `stream=false` で 90 秒後に bounded timeout され、sidecar `qwen3.5:9b` へ fallback した。
- fallback request も今回の修正どおり `stream=false` になったが、sidecar でも 90 秒 timeout が再発し、その後は同じ `qwen3.5:9b` request が再試行され続けた。
- plan file はテンプレートのままで、Plan mode から approval まで進まなかった。

## 問題箇所
- `src/agent/loop_run/turn.rs`
  - Plan timeout 時の degraded path が `main -> sidecar` までしかなく、`sidecar` も timeout した場合の最終退避先が無い。

## 根本原因
- `qwen3.5` 系の planning call が main / sidecar ともに応答しない場合、runtime は transport timeout を bounded できても、plan を前へ進める代替手段を持っていなかった。
- そのため timeout 自体は回収できても、substantive な plan が 1 行も書かれず、approval に必要な state へ到達できなかった。

## 対策案
- Plan mode で `main timeout -> sidecar timeout` まで到達したら、runtime が deterministic fallback plan を active plan file に materialize する。
- fallback plan は user request と task profile を使って full plan structure を埋め、approval 可能な形まで持っていく。

## 対策案詳細（仕様）
1. Plan mode で timeout が発生し、すでに `plan_model_override` が入っている場合は repeated planning timeout とみなす。
2. active plan file がまだ substantive でなければ、runtime が deterministic fallback plan を生成して上書きする。
3. fallback plan は最低でも `Goal`, `Constraints`, `Deliverables`, `Acceptance Criteria`, `Quality Bar`, `Execution Plan`, `Verification Plan`, `Risks / Fallbacks` を substantive に埋める。
4. plan materialization 後は assistant reply を synthetic に返し、approval prompt へ進める。
5. 回帰防止として、
   - repeated timeout 時に fallback materialization 判定が有効になる test
   - fallback plan が requested port などの task detail を含む test
   を追加する。

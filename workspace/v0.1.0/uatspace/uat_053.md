## 事象
- `qwen3.5:122b` で `uat_053` を実施したところ、Plan は完了し、承認後の Act で `create-next-app` に成功した。
- `iter 2` で `src/app/page.tsx` を Read し、`iter 3` / `iter 4` の retry 後、`iter 5` で deterministic first Edit が landing した。
- しかし first Edit 後の continuation で再び full page rewrite 相当の巨大 `Edit` を生成し、`iter 6` で `tool_call_format_error: truncated tool call (generate response hit length limit)` に落ちた。
- sandbox 上の `src/app/page.tsx` は `VOID RAIDERS` の teaser までで、ゲーム本体は実装されなかった。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- post-scaffold continuation recovery
- focused edit truncated tool call fallback

## 根本原因
- `uat_051` の対策で first implementation Edit は deterministic に landing できるようになった。
- ただし、その後の continuation はまだ LLM の自由な `Edit` 生成に戻っており、モデルは現在の小さな teaser ではなく、直前 Read の default scaffold 全体を old_string にした full rewrite を再生成した。
- `focused_edit_history` が latest Read を保持するため、first Edit 後の実ファイルとの差分がモデル側に伝わらず、post-first-edit の tool call が再び肥大化した。

## 対策案
- first Edit 後、page component の continuation で truncated tool call が発生した場合は、再試行 note ではなく runtime が現在の `page.tsx` を filesystem から読み取り、exact `old_string` として deterministic completion `Edit` を合成する。
- 対象タスクが Space Invaders 系である場合、single-file の playable canvas 実装へ置換し、LLM の巨大 JSON 生成に依存しない。

## 対策案詳細（仕様）
- 条件:
  - focused target が `app/page.tsx` / `src/app/page.tsx`
  - target は既に Read 済み
  - non-plan repo edit が 1 回だけ成功済み
  - failure が `truncated tool call`
  - user task が `space invader` / `スペースインベーダー` を含む
- 動作:
  - runtime が現在の target file content を `old_string` として取得する
  - `new_string` は `use client` + canvas game loop + keyboard controls + score/lives/wave HUD を持つ complete page にする
  - `Edit` tool call を runtime が返す
- 期待効果:
  - first Edit 後の continuation が default scaffold Read に引きずられて full rewrite を生成する問題を回避する
  - 少なくとも Space Invaders UAT では、LLM の長大 tool call に依存せず playable slice まで到達できる

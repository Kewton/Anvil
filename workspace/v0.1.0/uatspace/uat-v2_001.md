- 事象
  - qwen3.5:122b / sidecar qwen3.5:9b のE2E 1回目で、Next.js scaffold後に `missing_repo_edits` で停止した。
  - `src/app/page.tsx` は読まれており、focused edit recovery は `Edit` のみを許可していたが、モデルが `Read` を2回連続で出し、ポリシー拒否後に終了した。
  - 併発として auto-plan classifier が `<think>` 出力のみで長さ上限に到達し、JSON parseに失敗して heuristic fallback へ落ちた。

- 問題箇所
  - `src/agent/recovery.rs`
    - `post_scaffold_edit_recovery_note`
    - `forced_small_edit_recovery_note`
  - `src/agent/loop_run/turn.rs`
    - focused edit recovery 中のツール制限とプロンプト文言の整合

- 根本原因
  - focused edit recovery では対象ファイルが既読の場合に実行可能ツールを `Edit` のみに絞る一方、同一リクエスト内の recovery note に `Read or Edit` と `First inspect the file if needed` が残っていた。
  - その結果、ローカルLLMが「まずReadする」という判断を優先し、ランタイム側の focused edit policy により拒否され続けた。

- 対策案
  - 対象ファイルが既読の recovery note では `Read` を候補に出さず、`Edit` のみが利用可能であることを明示する。
  - post-scaffold recovery note は既読状態を受け取り、未読時のみ `Read or Edit` を許容する文言にする。
  - focused edit guidance でも既読時は `Edit` のみが利用可能であることを明記する。

- 対策案詳細（仕様）
  - `post_scaffold_edit_recovery_note(path, attempt, already_read)` に変更する。
  - `already_read == true` の場合:
    - `Read` / `Bash` / `Glob` / `Grep` / `Write` を使わないよう明示する。
    - 返答は対象ファイルへの exactly one compact `Edit` のみを求める。
  - `already_read == false` の場合:
    - 既存どおり最小限の `Read` または `Edit` を許可する。
  - `forced_small_edit_recovery_note` は直前Read済みのファイルを対象にするため、`Edit` のみを明示する。
  - 単体テストで既読時の post-scaffold note に `Read or Edit` / `First inspect` が含まれないことを検証する。

## 事象
- `uat_028` は empty workspace からの `ls -> prose only` 停滞は解消し、初手で `npx create-next-app@latest space-invaders ...` を実行して scaffold まで進んだ。
- しかし scaffold 後は `app/page.tsx` を読んだ同一ターンで `package.json` も読んだため、次ターンの focused recovery target が `package.json` にずれてしまった。
- その結果 `Read app/page.tsx` が `focused edit recovery only allows Read or Edit on package.json` で拒否され、その後も `src/app/*` への誤 Read を繰り返して `missing_repo_edits` で終了した。

## 問題箇所
- `src/agent/loop_run/turn.rs`

## 根本原因
- `post_scaffold_edit_recovery_target()` が `last_read_tool_path()` を優先しており、scaffold 直後に model が `app/page.tsx` と `package.json` を同一応答で並べると、最後に読んだ `package.json` が recovery target になっていた。
- これは「最初に実装へ入るべき既存ファイル」を `first_existing_impl_target()` で判定できる状況でも、直近 Read のノイズに引っ張られる設計だったため。

## 対策
- scaffold 後 recovery target は `last_read_tool_path()` より先に `first_existing_impl_target()` を優先する。
- つまり `app/page.tsx` / `src/app/page.tsx` などの実装対象が既に存在するなら、同一ターンで `package.json` や他ファイルを読んでも recovery target を乗り換えない。

## 期待効果
- scaffold 後の first edit が `app/page.tsx` に固定され、`package.json` 読みへの誤ロックを防げる。
- `uat_028` 型の「page を一度読んだのに config 側へ recovery target が逃げる」失敗を減らせる。

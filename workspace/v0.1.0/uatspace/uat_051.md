## 事象
- `qwen3.5:122b` で `uat_051` を実施したところ、Plan は完了し、承認後の Act で `create-next-app` に成功した。
- その後 `iter 2` で `Read src/app/page.tsx` までは安定して到達したが、次の `iter 3` で again `tool_call_format_error: truncated tool call (generate response hit length limit)` に落ちた。
- sandbox 上の `src/app/page.tsx` は default scaffold のままで、今回も first implementation `Edit` は landing していなかった。
- 失敗までの duration は `113s` で、`uat_050` より長く、post-read first `Edit` がまだ LLM retry に依存していた。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- post-read first `Edit` の truncated tool call error handling
- focused recovery note の再試行方針

## 根本原因
- `src/app/page.tsx` の exact anchor 特定まではできているが、first `Edit` の JSON body 自体がなお肥大化し、モデル retry を何回回しても landing しない。
- つまりボトルネックは「target の特定」ではなく、「first `Edit` の生成をまだ LLM の自由出力に任せていること」だった。
- `Read` 済み page component に対して exact `old_string` を既に持っている以上、この最初の小さな teaser patch は runtime 側で deterministic に合成できる。

## 対策
- `Read` 済み `src/app/page.tsx` / `app/page.tsx` で truncated tool call が起きた first `Edit` では、LLM retry note を増やす代わりに runtime が deterministic な compact `Edit` tool call を合成する。
- これで first implementation `Edit` を確実に landing させ、その先の continuation recovery に接続する。

## 対策案詳細（仕様）
- 条件:
  - focused target が page component
  - target は既に `Read` 済み
  - non-plan repo edit はまだ 0 回
  - failure が `truncated tool call`
- 動作:
  - last `Read` から抽出した exact `old_string` を使い、`h1`/`p` の intro copy を `VOID RAIDERS` の teaser 文面へ差し替える 1 回の `Edit` を runtime が合成して返す
  - `new_string` は title + score/lives/controls の 2 行相当だけに限定し、layout wrapper や imports は変更しない
- 期待効果:
  - first `Edit` の JSON 本体肥大化を runtime 側で回避し、post-read first `Edit` の landing 率を安定化する

# uat-v2_023

## 事象

qwen3.5:122b で Next.js の Space Invaders 指示を Act 実行したところ、`create-next-app` 後に `src/app/page.tsx` を読んで軽い編集を試みた後、次の assistant 応答待ちが 4 分以上継続した。

実ファイルは create-next-app の初期ページのままで、ゲーム実装には到達していなかった。

## 問題箇所

- `src/agent/loop_run/turn.rs`
  - focused edit timeout override が qwen3.5 系では 90 秒の floor に戻され、短い timeout が効いていなかった。
  - deterministic quality fallback を適用しても、その後に再度 LLM 応答へ戻っていた。
  - focused edit timeout 時に、既存ファイルが明らかな scaffold placeholder でも quality fallback へ短絡しなかった。

## 根本原因

local LLM が scaffold placeholder を小さく編集した後、次の方針生成で長時間固着する場合がある。
既存の品質ゲートは final reply の後に動くため、assistant 応答が返らないケースでは発火できなかった。

また fallback 適用後も再度モデルに戻る設計だったため、せっかく deterministic に playable UI へ置換しても、同じ不安定なモデル呼び出しに戻る余地があった。

## 対策案

- focused edit の timeout override は qwen3.5 系でもそのまま使い、30/45 秒で検知する。
- focused edit timeout 時、現在の依頼が playable UI で、対象ファイルが scaffold placeholder の場合は deterministic quality fallback を適用して assistant reply として返す。
- quality gate が deterministic fallback を適用した場合は、その場で Done にして再度 LLM へ戻さない。

## 対策案詳細（仕様）

- `effective_non_streaming_timeout_secs` は `timeout_override_secs` がある場合、モデルファミリに関係なく override を採用する。
- `maybe_apply_deterministic_quality_fallback_after_timeout` を追加する。
  - timeout error かつ Act mode の playable UI request のみ対象。
  - `accepted_repo_change_quality_issue` で scaffold/placeholder 問題を確認する。
  - `deterministic_playable_ui_fallback` が適用できる場合、対象ファイルを書き換え、tool call なしの完了 reply を返す。
- 通常の quality gate でも deterministic fallback 適用後は `ExitReason::Done` とし、追加の LLM 呼び出しを行わない。

## 事象
- `uat_016` で Next.js scaffold 後、`app/page.tsx` を `Read` したあとに `qwen3.5:122b` が巨大な full-file `Write` を繰り返した。
- 各 `Write` は `generate response hit length limit` で tool call が途中切れになり、実際の repo change に進まないまま長時間 retry が続いた。
- 表面上は `thinking...` が継続して見え、ユーザー体感では停止に近い。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- `src/agent/recovery.rs`

## 根本原因
- truncated tool call 後の recovery は note 追加だけで、次 turn の利用可能ツールや変更粒度を runtime 側で狭めていない。
- そのためモデルが既存ファイルに対して再び巨大な full-file `Write` を選び続け、同じ長さ制限エラーを再発させる。
- 特に scaffold 直後の `app/page.tsx` は既存ファイルなので、本来は小さな `Edit` から入るべきだが、その誘導が弱い。

## 対策案
- truncated tool call が Act mode の既存ファイル書き換えで発生した場合は、一時的に `Read` と `Edit` だけを許可する small-edit recovery mode に入る。
- recovery mode では直近に `Read` した対象ファイルを明示し、`Write` / `Bash` / `Glob` / `Grep` を禁止して、小さい `Edit` 1 回に集中させる。

## 対策案詳細（仕様）
- 発火条件:
  - `ExecutionMode::Act`
  - 直近の system note に `truncated tool call` recovery がある
  - まだ成功した repo edit がない
  - 直近の `Read` 対象ファイルが存在する
- 動作:
  - 次の LLM request では tool spec を `Read` と `Edit` のみに絞る
  - system note で `Edit` 対象 path と「1つの連続ブロックだけ、小さい編集」を明示する
  - 1回でも `Edit` / `Write` が成功したら recovery mode を解除する
- 期待結果:
  - `app/page.tsx` に対する巨大な full-file `Write` の再試行が止まる
  - 最初の repo change が小さい `Edit` に分割され、以後の実装が段階的に進む

## 事象
- `sandbox_0424/uat_012` で UAT を実施したところ、`main timeout -> sidecar timeout` の後に runtime fallback plan は正しく materialize された。
- しかしその直後、runtime は synthetic completion reply を `no_tool_reply` と誤判定し、approval へ遷移せず sidecar にもう 1 手投げ直した。
- セッションログでは `agent.plan.timeout_fallback_materialized` の直後に `agent.plan.stalled(reason=no_tool_reply, stage=ready)` が出ていた。

## 問題箇所
- `src/agent/loop_run/turn.rs`
  - `requires_action && tool_calls_made_this_turn == 0` の no-tool branch が、すでに substantive / approval-ready な plan を例外扱いしていない。

## 根本原因
- deterministic fallback plan は tool call を伴わず runtime 内で直接 materialize されるため、assistant reply 自体は prose-only になる。
- 現在の loop は `tool_calls_made_this_turn == 0` を先に見て recovery に入るため、plan file の actual state が `Ready` でも approval 完了として受理できていなかった。

## 対策案
- Plan mode の no-tool branch では、まず current plan contents を確認し、すでに substantive / approval-ready なら completion として受理する。
- それ以外の場合だけ既存の `plan_no_tool_recovery_note` を出す。

## 対策案詳細（仕様）
1. `requires_action && tool_calls_made_this_turn == 0` 分岐の `PlanProgress` ケースで current plan contents を読む。
2. `plan_is_substantive_with_fallback()` が true なら retry を行わず、その turn を `Done` として抜ける。
3. 既存の no-tool recovery は non-substantive plan にだけ適用する。
4. 回帰防止として、
   - ready な plan が no-tool branch でも受理される test
   を追加する。

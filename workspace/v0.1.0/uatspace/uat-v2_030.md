# UAT v2 030 incident

- Time: `2026-04-25 11:08:26 JST`
- Model: `qwen3.5:122b` with sidecar `qwen3.5:9b`
- Scenario: exact v2 UAT instruction 3, `Nuxt.js` Tetris game.
- Result: failed before completing the required four-instruction run.

## What Happened

The agent correctly chose a Nuxt scaffold command:

- `npx nuxi@latest init . --packageManager npm --force`

The empty-workspace framework policy rejected it as a non-scaffold command.
Afterward the loop blocked repeats, and the model drifted into hand-written
Nuxt bootstrap files (`package.json`, `nuxt.config.ts`, directories, CSS).

## Cause

The framework matcher accepted Nuxt-specific commands such as `nuxi`, but the
lower-level `is_scaffold_command` predicate only recognized generic
`npm create` / `pnpm create` / `yarn create` and `create-next-app` style
commands. This made the policy internally inconsistent: the recovery note told
the model to use `npx nuxi@latest init`, while the guard rejected that exact
path before framework matching could matter.

## Fix Direction

Treat Nuxt scaffold tools as scaffold commands at the shared recovery layer:

- accept `nuxi` as a scaffold command;
- accept `create-nuxt` as a scaffold command;
- keep the existing explicit framework matcher in place so these commands are
  still only valid when they match the requested framework.

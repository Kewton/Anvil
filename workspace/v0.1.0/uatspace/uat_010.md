## 事象
- `sandbox_0424/uat_010` で UAT を実施したところ、Plan mode Stage 1 の main model request は `assistant reply timed out after 90s` 相当で bounded され、sidecar `qwen3.5:9b` へ fallback した。
- しかし fallback 後の sidecar request も応答が返らず、TTY では `thinking... (qwen3.5:122b)` が継続し、plan file はテンプレートのまま 1 度も更新されなかった。
- セッションログでは fallback 後の request が `ollama.generate.request(model=qwen3.5:9b, stream=true)` になっていた。

## 問題箇所
- `src/agent/loop_run/turn.rs`
  - non-native tool path の streaming disable と hard timeout 短縮が `qwen3.5:122b` にしか適用されていない。

## 根本原因
- `qwen3.5` 系の non-native tool path で起きる stall を main model `122b` だけの例外として扱っていた。
- そのため、Plan timeout 後に fallback した sidecar `qwen3.5:9b` は再び `stream=true` の generate path に入り、同系統の stall を再発させていた。

## 対策案
- `qwen3.5` 系モデルはサイズに関係なく、non-native tool path では streaming transport を無効化する。
- 同じ条件で hard timeout も短縮し、fallback 後も bounded retry を維持する。

## 対策案詳細（仕様）
1. `turn.rs` に `qwen3.5` 系判定 helper を追加する。
2. `should_use_streaming_transport()` は `!native_tools_enabled && qwen3.5 family` なら `false` を返す。
3. `non_streaming_assistant_reply_timeout_secs()` も同じ条件で 90 秒を返す。
4. 回帰防止として、
   - `qwen3.5:9b` の non-native path が non-streaming になる test
   - `qwen3.5:9b` の hard timeout が 90 秒になる test
   を追加する。

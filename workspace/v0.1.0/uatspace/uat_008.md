## 事象
- `sandbox_0424/uat_008` で UAT を再実施したところ、`qwen3.5:122b` の main plan call を `stream=false` に切り替えても、Stage 1 の最初の assistant reply が 2 分超返らず spinner が継続した。
- セッションログでは `ollama.generate.request(stream=false)` が出た後、`ollama.generate.response_raw` も `ollama.generate.error` も追加されなかった。
- TTY では `thinking... (qwen3.5:122b)` が `139s` まで継続しており、`OllamaClient(timeout=120s)` の外側でも runtime が待ち続けていた。

## 問題箇所
- `src/agent/loop_run/turn.rs`
  - assistant reply は `request_assistant_reply()` を直接待機しており、runtime 側の hard timeout が無い。
- `src/agent/loop_run/lifecycle.rs`
  - transport error 判定が `timed out` 系の独自 error を吸収していない。
- `src/ollama/client.rs`
  - timeout 設定はあるが、この stack では non-streaming generate 呼び出し全体を確実に bounded にできていない。

## 根本原因
- `reqwest` / Ollama 側の timeout に依存しただけでは、`qwen3.5:122b` の一部 generate 呼び出しが hard hang したケースを runtime が回収できていなかった。
- そのため、model call が戻らないと loop 全体がその場で止まり、retry や fallback に進めない。

## 対策案
- runtime 側で assistant reply 全体に hard timeout を設け、一定時間で thread 越しに timeout error へ変換する。
- `qwen3.5:122b` の non-native tool path では、通常 timeout より短い hard timeout を適用して retry を早める。
- timeout error を既存の transport retry 判定に含める。

## 対策案詳細（仕様）
1. non-streaming assistant reply は worker thread で実行し、`recv_timeout()` で結果待ちする。
2. hard timeout は通常 client timeout を上限としつつ、`qwen3.5:122b + !native_tools_enabled` では 90 秒に短縮する。
3. timeout 時は `assistant reply timed out after Ns` を返し、既存の transport retry に乗せる。
4. `is_transport_error()` は `timed out` を transport error として扱う。
5. 回帰防止として、
   - hard timeout 秒数選択の unit test
   - `qwen3.5:122b` の bounded path 判定 test
   を追加する。

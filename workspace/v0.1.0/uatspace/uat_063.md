- 事象
  - `uat_063` で `qwen3.5:122b` の auto-plan 実行後、Act フェーズが `missing_repo_edits` で停止した。
  - Next.js scaffold と `src/app/page.tsx` の Read までは完了したが、その後 `Focused edit recovery requires exactly one compact tool call on the target...` の retry が繰り返され、要求されたゲーム実装の repository edit に進めなかった。
  - 終了時表示は `✘ missing_repo_edits iter 5/50 duration 56s edited 12 files`。

- 問題箇所
  - scaffold 後の focused edit recovery が、モデルに単一 Edit tool call を要求するだけで、qwen3.5 が従わない場合に deterministic first edit fallback へ進まない。
  - 既存の deterministic page first edit fallback は malformed / truncated tool call 回復経路に偏っており、no-tool / policy-retry 連続時には発火しない。

- 根本原因
  - qwen3.5 は `page.tsx` を読んだ後でも、編集対象と形式制約を満たす tool call を返さず、説明や不適切な行動に寄ることがある。
  - 現行実装は scaffold 後に実装対象ファイルを特定でき、まだ非 plan repo edit が 0 件の状態でも、no-tool / retry-only の停滞を安全な deterministic first edit に切り替えない。

- 対策案
  - Act mode の post-scaffold focused edit recovery で、対象ファイルが既読かつ非 plan repo edit が 0 件のまま retry が続く場合、deterministic first edit reply を返して最初の playable slice を強制的に入れる。
  - これは empty workspace Next.js task の scaffold 後に限定し、通常の任意編集へは広げない。

- 対策案詳細（仕様）
  - `focused_edit_recovery_target()` が存在し、対象が既読、`successful_non_plan_repo_edit_count == 0` の場合、no-tool / repo-change retry 経路でも `deterministic_page_first_edit_reply` を使えるようにする。
  - 発火時は LLM event を記録し、既存の deterministic completion fallback と同じく `AssistantReply` として通常 tool 実行ループへ戻す。
  - 対象は Act mode の scaffold/post-scaffold recovery に限定し、Plan mode や通常の transport/parser failure とは分離する。
  - 回帰テストを追加し、`cargo fmt --check`、対象テスト、`cargo test`、`cargo build --release` で検証する。

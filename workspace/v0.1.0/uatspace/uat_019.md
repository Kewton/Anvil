## 事象
- `uat_018` で Next.js scaffold は成功したが、その後の Act mode が安定して実装フェーズへ入らなかった。
- 具体的には `Read next.config.js` の直後に `ls -la ...`、さらに `find ...` のような broad Bash discovery へ戻り、`Bash loop blocked` に入った。
- その結果、最初の repo edit に到達せず、ユーザー体感では停止に近い。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- `src/agent/recovery.rs`

## 根本原因
- scaffold 後の recovery は「repo change after setup」の system note 追加まではあるが、次 turn の利用可能ツールを runtime 側で狭めていない。
- そのため `qwen3.5:122b` が `Read next.config.js` のあとに再び `Bash ls/find` を選び、scaffold 直後の broad discovery に逆戻りする。
- 既存の `Bash loop blocked` は発火しても、その後の次手を `Read/Edit` に強制しないため、loop 収束が弱い。

## 対策案
- scaffold 成功後、最初の repo edit が入るまで一時的な post-scaffold small-edit recovery mode に入る。
- recovery 中は `Read` と `Edit` だけを許可し、直近に読んだ実装ファイル、または代表的な entry file を target に固定する。

## 対策案詳細（仕様）
- 発火条件:
  - `ExecutionMode::Act`
  - 直近メッセージ列に scaffold Bash command が存在する
  - まだ成功した `Write` / `Edit` がない
- 動作:
  - 次の LLM request では tool spec を `Read` と `Edit` のみに絞る
  - system note で「scaffold は終わっているので Bash/Glob/Grep に戻らず、既存ファイルを小さく編集する」ことを明示する
  - target file は `last_read_tool_path` を優先し、なければ `app/page.tsx` / `src/app/page.tsx` / `app/globals.css` / `next.config.ts` などの既存ファイルから選ぶ
  - 最初の成功した repo edit が入ったら recovery mode を解除する
- 期待結果:
  - scaffold 後の `ls/find` ループが止まる
  - 最初の実装 edit に到達し、その後の実装と検証が段階的に進む

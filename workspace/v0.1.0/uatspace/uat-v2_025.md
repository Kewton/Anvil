# uat-v2_025

## 事象

qwen3.5:122b で 4 指示セットを再開したところ、1 本目の Space Invaders / Next.js は `Quality fallback` により完了した。
しかし 2 本目の Breakout / React.js で、空ワークスペースに Next.js scaffold が作成され、`src/app/page.tsx` の見出しだけを `NEON BREAKOUT` に変えた後、quality gate が「モデルに placeholder 置換を依頼」する経路に入り、その後 2 分以上応答待ちで固着した。

## 問題箇所

- `src/agent/loop_run/quality.rs`
  - deterministic quality fallback の placeholder 判定が、依頼から推定した framework の scaffold marker だけを見ていた。
  - React.js 依頼で Next.js scaffold が作られるような framework mismatch では、`next.svg` / `vercel` / `nextjs.org/docs` などを placeholder として検出できなかった。
  - Breakout 種別推定が `breakout` / `ボール崩し` のみ対応で、UAT 文面の `ブロック崩し` を Breakout と判定できなかった。
- `src/agent/loop_run/turn.rs`
  - fallback が適用できない場合はモデル修正依頼へ戻るため、qwen3.5 が長時間固着する余地が残った。

## 根本原因

local LLM はユーザーの framework 指定と異なる scaffold を選ぶことがある。
品質判定は「出力ファイルが scaffold placeholder か」を見たいのに、「依頼 framework の典型 marker」だけに依存していたため、実際の scaffold 種別とズレると決定的修復へ進めなかった。

さらに日本語のゲーム名揺れを吸収できず、仮に fallback しても Breakout ではなく既定の Invaders に落ちる可能性があった。

## 対策案

- placeholder 判定は依頼 framework だけでなく、Next / React / Nuxt / Unknown の scaffold marker を横断的に見る。
- framework mismatch でも placeholder が含まれる UI ファイルなら deterministic playable UI fallback を適用できるようにする。
- `ブロック崩し` も Breakout として扱う。
- これにより、quality gate が発火した後にモデルへ再修正させる頻度を下げる。

## 対策案詳細（仕様）

- `placeholder_hit_count(framework, normalized_content)` を追加する。
  - 依頼 framework の marker。
  - Next scaffold marker。
  - React/Vite scaffold marker。
  - Nuxt scaffold marker。
  - 汎用 placeholder marker。
- `implementation_quality_issue_for_request` と `deterministic_playable_ui_fallback` はこの共通 hit count を使う。
- deterministic fallback は framework mismatch でも、対象 path が `.tsx` / `.jsx` / `.ts` / `.js` / `.vue` なら既存テンプレートに置換する。
- `GameKind::from_request` は `breakout` / `ボール崩し` / `ブロック崩し` を Breakout とする。

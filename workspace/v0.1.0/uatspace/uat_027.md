## 事象
- `uat_027` は 10 秒で `missing_repo_edits` 終了、変更ファイル 0 件だった。
- session 上では最初に `cd ... && ls`、次に `ls -la .../uat_027/` を実行したあと、repo change recovery note が 2 回入っている。
- それにもかかわらず、次の assistant reply は `Let me scaffold a Next.js project and then implement the Space Invaders game.` という prose のみで、tool call を出さずに終了した。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- `src/agent/recovery.rs`

## 根本原因
- repo change recovery は system note で「次は Write/Edit を出せ」と促しているが、モデルが tool を出さず prose で終了した場合、runtime は最終的に retry / fail するだけで、tool-first へ強制的に収束させる実行段の仕組みがない。
- つまり `focused edit recovery` のような強制ゲートが効く前段で、そもそも scaffold/inspection 以降の first tool selection を prose-only 応答に奪われる経路が残っている。

## 対策案
- repo-change 必須状態では prose-only reply を許可せず、次ターンを generic retry に戻すのではなく「tool call なし reply は無効」として即 recovery note を強化する。
- とくに empty workspace では、最初の scaffold tool call を deterministic に補助する fallback を追加し、`ls` だけで終わる探索 turn を短く切る。

## 対策案詳細（仕様）
- `ActionExpectation::RepoChange` かつ final reply に tool call なし、repo edit なしのとき:
  - empty/full prose を同じ violation とみなし、専用 note を追加する
  - note には `Do not answer in prose. Emit exactly one tool call now.` を含める
- empty workspace 判定時は、`first_existing_impl_target` がなく `capture_repo_snapshot` も空に近い場合、scaffold fallback guidance を追加する
- 期待結果:
  - `uat_027` 型の「ls -> ls -> prose only -> fail」を減らす
  - first actionable tool call までの到達率を上げる

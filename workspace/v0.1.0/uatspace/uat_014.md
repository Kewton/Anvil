## 事象
- `uat_014` で Plan は完了し、Act でも `create-next-app`、`next dev -p 3011 &`、`curl http://localhost:3011` までは進んだ。
- ただしその後、`qwen3.5:122b` が `src/app/page.tsx` 向けと思われる巨大な `Write` tool call を出力し始め、`done_reason=length` で途中切れになった。
- runtime は parse error として retry したが、その後も長い推論に戻り、実装完了まで進まない。

## 問題箇所
- `src/agent/recovery.rs`
- `src/agent/loop_run/commands.rs`

## 根本原因
- classifier failure 時の heuristic fallback がこの依頼を `generic` と見なしており、Act prompt が coding task として十分に絞り込まれていない。
- その状態で `qwen3.5:122b` は `src/app/page.tsx` 全文を書き換える大きな `Write` を出しやすく、`num_predict=2048` 上限で tool call JSON が途中切れになる。
- 現在の `tool_call_format_recovery_note()` は「small にしろ」としか言わず、`Read -> small Edit` へ具体的に矯正できていない。

## 対策案
- heuristic fallback が Next.js / React / app / アプリ系依頼を `coding` と判定するようにする。
- truncated tool call recovery を具体化し、巨大 `Write` 再試行ではなく `Read` と小さな `Edit` に強制的に寄せる。

## 対策案詳細（仕様）
1. `infer_task_profile_from_text()` に `next.js`, `react`, `typescript`, `app`, `web app`, `アプリ`, `ゲーム` など coding 寄りの語を追加する。
2. classifier unavailable 時でも、この依頼は `task_profile=coding` で Plan / Act に入るようにする。
3. `tool_call_format_recovery_note()` は、error に `truncated tool call` を含む場合:
   - 「前回の tool call は長すぎて切れた」
   - 「次は full-file Write を禁止」
   - 「まず Read、次に短い Edit または短い Write を 1 回だけ」
   - 「コード/JSON 本文を 1 回で大量に送らない」
   を明示する。
4. unit test で以下を確認する。
   - Next.js / アプリ系文面が heuristic で `coding` に分類されること
   - truncated tool call recovery note に `Read` / `Edit` / `full-file Write` 回避の文言が含まれること

# uat-v2_024

## 事象

qwen3.5:122b で Next.js の Space Invaders 指示を再開したところ、`create-next-app` 後に `src/app/page.tsx` を読み、scaffold placeholder を一部編集した後、次の assistant 応答待ちが 2 分以上継続した。

直前の修正で focused edit timeout と timeout 時 quality fallback を追加していたが、実行は完了せず、手動停止が必要になった。

## 問題箇所

- `src/agent/loop_run/turn.rs`
  - tool 実行直後の quality gate で deterministic quality fallback を適用した後、`continue` により次の LLM 応答へ戻っていた。
  - そのため、placeholder は置換できても、完了判定に進まず同じ不安定な qwen3.5 応答待ちに再突入していた。
- `src/agent/loop_run/quality.rs`
  - Plan 承認後の active task が「承認された計画を実行せよ」というラッパー文になり、元の「ゲームを作る」指示を playable UI quality gate が見失う場合があった。

## 根本原因

scaffold placeholder を deterministic に playable UI へ置換できた時点で、ユーザー要求の最低品質は満たせる。
しかし既存制御は「修復後にモデルへ再確認させる」流れを残しており、local LLM が長時間固着するケースでは、修復済みの成果物を完成として扱えなかった。

また Plan/Act 遷移ではユーザー入力として実行用プロンプトを再投入するため、品質判定に使う request text が元の依頼ではなく実行ラッパーになることがあった。
その結果、ゲーム/interactive UI 向けの決定的フォールバックが適用対象外になる場合があった。

## 対策案

- tool 実行直後の quality gate でも、deterministic quality fallback が成功した場合は即座に `ExitReason::Done` にする。
- 完了メッセージには置換対象ファイルを含め、追加の LLM 呼び出しを行わない。
- final reply 後の quality fallback と同じく、修復できた成果物をその場で完了扱いに統一する。
- quality gate の request text は、active task が Plan/Act のラッパー文の場合、過去の plan 作成プロンプト内の `User request:` から元指示を復元する。

## 対策案詳細（仕様）

- `repo_edit_calls_made_this_turn > 0` の quality gate 内で `maybe_apply_deterministic_quality_fallback` が `Ok(true)` を返した場合:
  - 進捗行として `Quality fallback` を表示する。
  - `final_prose` に完了文を設定する。
  - `exit_reason = ExitReason::Done` を設定する。
  - actor loop を `break 'outer` で終了する。
- この経路では LLM に追加応答を求めない。
- `repo_change_request_text` は以下の優先順位で依頼本文を返す。
  1. active task 内の `User request:` 以降。
  2. active task が承認/plan ラッパーでない場合は active task 自体。
  3. セッション履歴の user message 内の最新 `User request:`。
  4. 承認/plan ラッパーでない最新 user message。

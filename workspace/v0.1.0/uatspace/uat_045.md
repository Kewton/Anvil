## 事象
- `qwen3.5:122b` で `uat_045` を実施したところ、Plan は self-rewrite を繰り返しつつ最終的には承認待ちまで到達し、承認後に Act へ進んだ。
- Act では scaffold Bash、`next.config.ts` の `Write`、`src/app/page.tsx` の `Read` までは進んだが、その直後に `thinking...` が 120 秒超継続して停止した。
- 同 run では `src/app/page.tsx` の前に `app/page.tsx` への exploratory `Read` も一度混ざっていた。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- focused post-read turn の transport 選択と timeout 適用

## 根本原因
- `focused_edit_timeout_override_secs(...)` と `focused_edit_max_predict_override(...)` は non-streaming path にしか効かない。
- しかし TTY での UAT 実行では、`qwen3.5:122b` が native-tools enabled のまま streaming transport を通るため、post-read focused turn が bounded path に入らず、`src/app/page.tsx` 読み取り後も 120 秒超の長考が継続した。
- つまり「focused edit 用 recovery note は入っているが、実行 transport がその前提に合っていない」状態だった。

## 対策
- `Read` 済み focused edit turn では streaming transport を使わず、強制的に non-streaming path へ落とす。
- これにより 45 秒 timeout と 640 `max_predict` override を確実に適用し、timeout 時は focused recovery note へ切り返せるようにする。

## 対策案詳細（仕様）
- `focused_edit_timeout_override_secs(...)` か `focused_edit_max_predict_override(...)` が有効な turn では `should_use_streaming_transport(...)` の結果に関係なく non-streaming を使う。
- 上記は post-read focused turn のみに限定し、通常の streaming UX や他モデルの通常 turn は維持する。
- 追加で回帰テストを入れ、native tools が有効でも focused post-read turn は streaming を使わないことを固定する。

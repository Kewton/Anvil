## Additional Consideration: Non-TypeScript / Other Frameworks / Non-Coding

### Guard Added

Added regression coverage in `quality.rs` so deterministic framework fallback does not claim:

- Python CLI requests.
- SvelteKit requests, which are outside the current deterministic framework set.
- README-only improvement requests.
- Python CLI quality-improvement requests.

This prevents TypeScript/Next/React/Nuxt deterministic templates from being applied to unrelated work.

### Probe Results

- Python CLI probe: request correctly avoided UI deterministic fallback and entered normal LLM/tool flow. It created `sample.csv` but did not complete the CLI script within the bounded run. This confirms fallback isolation, but also shows non-TypeScript implementation performance is still weak without a dedicated small-file fallback or stronger tool-use recovery.
- Non-coding README summary probe: request correctly avoided UI fallback, but the agent still expected repository edits and hit max iterations despite the user saying not to modify files. This is a real product gap for non-coding usage.

### Direction

- Do not add broad deterministic templates for every language/framework. That would recreate template bloat and keyword coupling.
- Add a task-intent split before repo-edit recovery: `answer_only`, `docs_edit`, `code_edit`, `ui_scaffold`, `ui_polish`.
- For non-TypeScript coding, prefer generic small-file creation policies and normal tool use first. Add deterministic fallback only for narrow, high-confidence scaffolds such as a single-file Python CLI with sample input and a smoke command.
- For unsupported web frameworks such as SvelteKit/Astro/Solid, route to normal LLM implementation and quality checks, not Next/React/Nuxt templates.
- For non-coding use, allow read-only answer completion without forcing repository edits.

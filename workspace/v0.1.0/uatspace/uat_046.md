## 事象
- `qwen3.5:122b` で `uat_046` を実施したところ、Plan は承認まで進み、Act でも scaffold は成功した。
- ただしその後、`src/app/page.tsx` が存在する workspace で `Read app/page.tsx` の誤 path が混ざり、さらに recovery 中に `ls -la <sandbox>` 系の Bash が差し込まれた。
- 最終的には `iter 6`、約 244 秒で `tool_call_format_error: truncated tool call (generate response hit length limit)` に到達し、`src/app/page.tsx` は default scaffold のまま未編集だった。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- focused edit turn の timeout / max_predict override 適用条件
- focused tool-call-format / timeout recovery の pre-read 分岐

## 根本原因
- 既存の bounded 化は「target file を正しく `Read` 済み」の focused turn にしか効いていなかった。
- そのため、モデルが最初の focused turn で誤 path `Read app/page.tsx` や不正な追加 tool を出した場合、そのターンは still-streaming / unbounded のまま残り、長考の末に truncated tool call まで膨らんだ。
- つまり `post-read focused edit` だけを守っており、「target は見えているがまだ正しく読めていない focused turn」の制御が弱かった。

## 対策
- focused target が存在する turn では、target 未読でも bounded non-streaming path に落とす。
- target 未読のまま timeout / truncated / unterminated tool-call-format error が出た場合は、次ターンを「その target への単独 `Read`」に収束させる専用 recovery note を返す。

## 対策案詳細（仕様）
- `focused_edit_timeout_override_secs(...)` と `focused_edit_max_predict_override(...)` は post-read だけでなく pre-read focused turn にも適用する。
- pre-read は `30s / 320 max_predict`、post-read は既存どおり `45s / 640 max_predict` として、first `Read` を短く収束させる。
- `truncated tool call` / `unterminated <anvil_tool_call> block` / timeout の recovery note は、target 未読時は `Edit` ではなく「exactly one Read on {target}」を要求する。
- これにより `src/app/page.tsx` の exact `Read` を先に固定し、その次の turn で compact `Edit` へ進ませる。

- 事象
  - qwen3.5:122b の3つ目（Nuxt.js テトリス）で `app/app.vue` の Nuxt 初期画面を読み込んだあと、100秒以上 thinking が続いた。
  - その後の出力は `app/app.vue` にテトリス断片を追加したが、既存の `<NuxtWelcome />` と二重 `</template>` が残る不正な Vue ファイルになった。

- 問題箇所
  - `src/agent/loop_run/turn.rs`
    - 品質フォールバックは主に repo edit 後に走るため、read-only の探索で明確な scaffold placeholder を発見しても次の LLM ターンに進んでしまう。
  - `src/agent/loop_run/quality.rs`
    - Nuxt 初期画面自体は検出できているが、検出結果を read-only ターン直後に利用する経路がない。

- 根本原因
  - Nuxt/Vite/Next などの scaffold 直後は、対象ファイルを読んだ時点で「プレースホルダーであり、ユーザー要求を満たしていない」と確定できる。
  - しかし現状は、読み込み後にモデルへ編集を任せるため、ローカルLLMが長考したり、既存テンプレートの一部を残した不完全編集を行う余地がある。

- 対策案
  - Act モードで playable UI 品質ゲート対象のリクエスト中、tool turn が read-only でも実装対象ファイルに scaffold placeholder 品質問題が見つかったら、決定的フォールバックを即時適用してターンを完了する。
  - これにより Nuxt 初期 `app/app.vue`、Next 初期 `app/page.tsx`、Vite React 初期 `src/App.tsx` を読んだ直後に安定した canvas 実装へ置換できる。

- 対策案詳細（仕様）
  - tool 実行後のループで `repo_edit_calls_made_this_turn == 0` かつ `tool_calls_made_this_turn > 0` の場合も、`accepted_repo_change_quality_issue()` を評価する。
  - `deterministic_playable_ui_fallback()` が置換を返す場合は対象ファイルを書き換え、`Quality fallback` として `Done` 終了する。
  - 通常の非ゲーム/非UIリクエスト、または placeholder 判定できない既存実装には影響させない。

## 事象
- `uat_022` では Plan mode 完了後に `yes` で Act mode へ遷移したが、Next.js scaffold 後の最初の実装 edit に入れず長時間停止した。
- ログ上は `app/page.tsx` の full-file `Write` が length で切れたあと、runtime が `Read/Edit` 限定 recovery に入っている。
- しかしその次の LLM request が長時間返らず、90 秒 timeout と retry を繰り返して実質 stall した。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- `src/agent/loop_run/commands.rs`

## 根本原因
- Act mode の first-edit recovery でも、通常どおり `session.messages` 全体を request に積んでいる。
- その履歴には古い `[Plan Mode / ...]` note、plan progress recovery note、plan file の Read/Write transcript、compact summary、repo context、working memory が同居しており、scaffold 後の「最初の 1 edit」に対して文脈が重すぎる。
- その結果、qwen3.5:122b が recovery 指示を理解する前に再び大きい実装を考え込み、non-streaming tagged-tool path で長時間停止する。

## 対策案
- `approve -> act` で plan-only system note を session から落とす。
- `forced_small_edit` / `post_scaffold_edit` の recovery 中は request history を最小化し、最新の user request、act summary、対象 file の直近 `Read` だけを渡す。

## 対策案詳細（仕様）
- `approve_plan_mode` 実行時に、以下の system note を session から除去する
  - `[Plan Mode / ...]`
  - `[Plan File Alias]`
  - plan progress / plan no-tool / repeated exploration など plan-only recovery note
- `build_request_messages` に focused edit recovery path を追加する
  - 条件: `forced_small_edit_recovery_target` または `post_scaffold_edit_recovery_target` が存在する
  - このとき `Working Memory` と `Repo Context` は注入しない
  - 代わりに、以下だけを request に残す
    - 現在の Act system prompt
    - 最新の `[Act Mode / ...]` note
    - 最新の user request
    - 対象 file に対する直近の `Read` tool call とその result
    - focused edit recovery note
- focused edit recovery 中は専用の short guidance を追加する
  - 例: `Use exactly one compact Edit on the existing file. Do not attempt a full-file rewrite.`
- 期待結果:
  - scaffold 後の最初の repo edit request が軽くなる
  - 古い Plan mode note が Act request に混ざらない
  - `app/page.tsx` の最初の `Edit` が 1 turn 以内に出やすくなる

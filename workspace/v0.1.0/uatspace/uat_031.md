## 事象
- `uat_031` は `--cwd` を明示した再実行で home-dir hang を回避できたが、empty workspace で最初の scaffold に入らず失敗した。
- session では `Bash` による scaffold intent の後、`Write package.json` が 3 回続き、sandbox 側には `package.json` しか残らなかった。
- partial-progress recovery は future-intent prose を reject できていたが、manual bootstrap の反復自体は止め切れていなかった。

## 問題箇所
- `src/agent/loop_run/turn.rs`
- `src/agent/recovery.rs`

## 根本原因
- empty workspace 向け guidance は「scaffold するか first file を直接作るか」の generic note に留まっており、task が明示的に Next.js を要求している場合でも manual bootstrap を禁止していなかった。
- そのため model は `create-next-app` が blocked / loop 扱いになった後、`package.json` だけを手書きして前進したつもりになる逃げ道を選べた。
- repo-change partial-progress retry は「future-intent prose で止まるな」は補正できても、「framework task では scaffold Bash 以外を最初に許さない」という実行制約までは持っていなかった。

## 対策
- empty workspace かつ task が Next.js 明示のときは、system note で manual `package.json` / placeholder file bootstrap を明示的に禁止する。
- 実行段でも、scaffold 成功前は `Bash` 以外の tool call を reject し、`Bash` でも scaffold command 以外の `cd` / `ls` / manual bootstrap を reject する。
- これにより `uat_031` 型の `scaffold intent -> package.json hand-write loop` を runtime で切り落とし、最初の有効 action を framework scaffold に限定する。

## 期待効果
- explicit framework task の empty workspace 初動が安定して scaffold Bash に収束しやすくなる。
- post-scaffold recovery へ入る前に manual bootstrap へ逸脱する経路を減らせる。
